# Changelog

Every notable change to the provui workspace, newest first. The crates share
one version number and one release, so this is the changelog for all of them;
the scope on a bullet (`**core**`, `**tui**`) says which surface moved.

The `## Unreleased` region below is generated by `dx changelog --write` from
the commits since the last tag, and `dx release` cuts it into a released
section. Everything outside that region is handwritten and stays that way —
including a release intro, when a release wants a narrative rather than a list.
**Behavioural changes** is generated too, from `Behavioural-change:` trailers
on the commits themselves; write one on any commit a frontend would notice
after upgrading without editing a line of its own code.

Only `provui-core` reaches crates.io. `provui-tui` is `publish = false`: it is
the checkout's own frontend, run with `cargo run -p provui-tui -- <file>`, and it
still moves with the workspace version and still appears here — publishing is
the only thing it is out of. `cargo publish --workspace --dry-run` is the
current answer to what goes up, and no prose here tries to be.

One irregularity, recorded rather than tidied away: **0.1.0 and 0.1.1 went to
crates.io by hand on 2026-09-02**, with no changelog and no workflow; the tags
are at `23182b2` and `88c0eb8`, the same day. Their sections below were
generated after the fact from those commit ranges. Everything from the next
release on goes up through `publish.yml`.

### Behavioural changes

- the metadata pane is now to the right of the body rather
than above it, at a third of the width and the full height; flower falls back
to its single-pane page view below about 190 columns, where the band used to
give it the full width. Clicks and the wheel in the metadata pane now move
flower's cursor, where they were previously inert.

- the `prov` floor is now 0.12. The reader's
  behaviour is unchanged for every workspace 0.11 could parse; what
  0.12 changes in what an archive means — a top-level `prov.yaml` read
  without the root naming it, `views.<name>.under` resolved by title —
  reaches a session opened over that archive.

- a config document carrying `created`, `root`,
  `fields.<name>.under`, `fields.<name>.default`, or a field declared as
  a list now edits under a rule where before each row was ungoverned text.

- a document below an index that a field is declared
  `under:` is now edited with that declaration's type, vocabulary and
  open/closed rule, where it was previously edited as free text. A closed
  vocabulary therefore starts rejecting values outside it in those
  documents. A document outside every scope is unchanged.

- `Facets::of_key` answers `Field` for a key declared
  only under indexes, where it previously answered `Carried`.

## v0.1.1 — 2026-09-02

### Fixed

- **config-schema** — follow prov 0.11 — fixity is off/on, and deletions are recorded, not binned ([`a68adc3`](https://github.com/diaryx-org/provui/commit/a68adc3c1e6b278cd94c9afa4c7aea195636b4f6))

### Behavioural changes

- the config-document schema's `fixity` picker offers
`off`/`on` rather than `off`/`attachments`/`all`, and governs
`record_deletions` (a toggle, `ConfirmExplicitly` when turned off) instead of
`recycle_bin`. A frontend rendering the config document sees the row for
`recycle_bin` become untyped and a new typed row for `record_deletions`; the
root's inline `prov:` block follows, since it is the same rule list re-rooted.

## v0.1.0 — 2026-09-02

### Added

- the frontend-neutral UI composition core over prov + flower + leaf ([`fb3cbae`](https://github.com/diaryx-org/provui/commit/fb3cbae5ff95d27b5b3e6e18409a2363af30aa20))
- **tui** — the first frontend, leaf over the body and flower over the frontmatter ([`43ffb72`](https://github.com/diaryx-org/provui/commit/43ffb72651bee4c152241ef77c02d11a48270477))
- recognize prov's own frontmatter, and follow the links in it ([`1d95162`](https://github.com/diaryx-org/provui/commit/1d951621d7e3c601118402d05c2c51b038f6e773))

### Behavioural changes

- `provui-core` now requires `flower-core` 0.3.2, where it
 asked for 0.3.1. A patch-level move inside the same compatible range, so only
 a caller pinned to exactly 0.3.1 has to do anything. `leaf-core` deliberately
 stays at the newest *published* 0.1.4 even though the leaf checkout here is
 0.1.5: `provui-core` is publishable, and a requirement no registry can satisfy
 would make it unbuildable for anyone without these checkouts. Both are pinned
 to a patch level rather than left loose because the widget crates path-depend
 on their cores, and a requirement wide enough to admit an older registry copy
 lets a lockfile keep one — at which point the patch goes unused and the graph
 quietly holds two `Model`s and two `Doc`s that are not the same type.

- `schema_from_config` emits rules for prov's kernel
  frontmatter keys (`title`, `id`, `content`, `manifest`, `attachment`,
  `content_hash`, the configured `updated` field) and for the root's inline
  `prov:` policy block. A path that previously resolved to no rule may now
  resolve to one, so a frontend that treats "no rule" as "free text" will start
  drawing typed widgets for those keys — `attachment` in particular becomes a
  boolean and rejects `yes`. Rules for declared `fields` and relations are
  unchanged and still match first.

- `DocumentSession` now builds its metadata model with
  `Model::with_managed` rather than `Model::new`. With no `derived` keys supplied
  (every existing constructor) the behaviour is identical; `open_managed` is the
  new entry point that supplies them.
